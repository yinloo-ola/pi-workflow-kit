## Commits & Repository Hygiene

- **Explicit-path commits: verify the staging list against `git status` before committing.** Dir-scoped adds (`git add -- docs/ skills/`) silently exclude root-level files (README.md, CHANGELOG.md) that the same requirement edited — the committed suite goes red at HEAD while the worktree stays green. After staging, a one-line `git status --short` check (or adding the root files explicitly) catches it before the commit lands.
- **Keep one commit per topic in docs/plans/.** When more than one in-flight brainstorm has artifacts under docs/plans/, a bare `git add docs/plans/` sweeps unrelated drafts into the topic commit. Reset --soft HEAD~1, then re-commit with explicit `-- <files>` per topic so each change carries only its own design + progress (and any parked `*draft`/`*revised` files land on their own commit). Mirrors the same hygiene as `pwk-finalizing` use of the `????-??-??-<topic>-*` glob instead of bare `*<topic>*` (and, since the one-folder-per-topic layout, scoping disposal to the topic folder `docs/plans/<date>-<topic>/`).
- **A commit cannot record its own hash, and a generated artifact must not be committed inside its own range.** Two coupled traps: (1) writing a commit's SHA into a file and then committing that file means `--amend` changes the SHA you just recorded, so record it in a *follow-up* commit (`docs: record R<n> commit in progress`) and never assume the hash you read is the one that ships; (2) a review packet or similar generated summary that covers `merge-base..HEAD` must be built *after* the range is fixed and committed separately — otherwise it is swept into a commit inside its own diff, and regenerating it makes the packet contain its previous self (observed: 1787 → 3524 lines, entirely self-referential). Check `git status --short` before staging generated artifacts. The preventive is to keep them **untracked** (`git rm --cached <packet>`) rather than relying on the check: a broad `git add -A` defeats a status glance made one command earlier, which is how a regenerated packet was swept into a commit — and into its own diff range — a second time.

## Cross-Cutting Changes

- **A cross-cutting change must enumerate its consumers by concept, not by the phrase you edited.** When a discovery pattern changes (recursive glob, new folder layout, renamed suffix), sweep every site that uses the same pattern — not just the ones the design listed. The `completed/` exclusion initially missed a skill because neither the design's site list nor the tests' site arrays mentioned it; only a reviewer's repo-wide glob sweep caught it. Prefer asserting the invariant repo-wide (no unexcluded `docs/plans/**` discovery glob anywhere) over mirroring an enumeration that shares the design's blind spot. **The same applies to any cross-cutting claim, not just globs:** changing a default, a count, or a tag vocabulary means grepping every site that *states* it, including sites the design never listed — a review found three guides still asserting the old "four reviewers, unconditionally" wording plus a fourth still calling `parallel` the default, after the default changed; the same audit found a stale "one mandatory checkpoint" claim that ignored a third existing stop (the conditional `## Setup` checkpoint). Enumerate consumers by **concept**, never by the phrase you happened to edit.
- **Skill instructions that depend on shell/tool semantics state the invariant and name the trap — not the tool.** Model tool-choice variance produces confidently wrong results (non-interactive bash runs with globstar off, where `**` silently degrades to one directory level), and mandated commands age badly per-platform. Write the outcome invariant ("recursively list X reaching the nested folders, skipping Y"), one example command as a fallback, and the environment fact that breaks the naive approach.

## Editing Skills and Docs

- **Test-first for skill/doc content:** add the skill-lint assertion first (red — the skill doesn't yet claim the behavior), then edit the skill markdown to satisfy it (green). After edits run biome — it collapses short `if (cond) ok();` to one line and rejects array holes like `[, ""]` (restructure instead).
- **Anchor edit-tool oldText on apostrophe-free text.** These docs use curly apostrophes (U+2019) in contractions and possessives; an oldText written with a straight ASCII apostrophe fails to match silently and aborts the whole edit batch (zero blocks replaced). Pick anchors that avoid apostrophes, and rephrase newText to stay apostrophe-free for consistency.
- **After a rewording edit to a doc paragraph, re-read the full sentence, not just the replaced span.** The edit tool swaps the matched span, not the intent — a partial paragraph replacement leaves duplicated contradictory remnants behind the new text (one shipped as "...and neither do design docs (execution summary, review reports, code digest), and never open design docs"). Re-read the surrounding clause and run the wording assertions before committing.
- **Wording bans must scope to the defining line, not the whole file.** A blanket `/feature-complete-paused/` absence assertion broke on the resume map's legitimate legacy mention. When a doc both defines a thing and references its legacy predecessor, assert absence on the extracted definition line (e.g. the `Feature phase is one of:` line) and keep the blanket ban off the file.
- **A line-scoped text detector is both evadable and over-eager — pair it with a structural check.** Co-occurrence regexes on a single line miss a declaration wrapped across two lines, and they fire on your own remediation prose (an explanatory sentence mentioning both `Checkpoints` and `spec` keeps failing the "the enum must not list spec" assertion). Detect the *structural token set* (the pipe-separated vocabulary actually parsed from the tag line) and keep the prose scan scoped to the defining line.
- **Structured markdown templates must prescribe list-form lines.** A bare label line followed by indented continuation lines is a lazy continuation in CommonMark — every renderer merges the block into one run-on paragraph (observed: the digest Flow template rendered as a wall of text). Use bullets, headings, or fences for any structure a reader is meant to see as separate lines; the Flow span now has a property test, but other template fences can reintroduce the pattern.
- **Shape changes land on the writers; extraction anchors stay byte-identical.** When a rendered shape must change, edit only the emit sites (templates, emitters) and never move what consumers match on — line starts, `^…$` anchors, fixed-width slices, `startswith` offsets. A separator-only change (a blank line between fields) then parses old and new files for free — no migration, no format sniffing, no consumer edits — while re-forming the block as a list or hard breaks breaks every anchor and forces a multi-file re-anchor for the same cosmetic gain. Blank lines need no trailing-whitespace tricks: a single newline is a soft break in CommonMark, so the blank line is the anchor-stable paragraph separator.

- **A new content lint's first run over a live corpus surfaces stragglers — reconcile each, never exempt silently.** Expect sites the design inventory missed. Every failure gets an explicit decision: frame the sentence, or deliberately pin the recipe in the rule's allowlist with a comment saying so. The pins are policy and extending them is a reviewed decision — a catch-all exemption to make the run green silently deletes the policy.
- **Generating a code file whose content contains markdown fences: write it from a JSON-encoded literal, not a template literal.** Nested backtick escaping (fences inside template literals) is corrupt-prone and fails only at transform time, several steps after the write. Hand the literal content through a non-evaluated channel (a data parameter) and keep generator code free of backtick soup.
- **Widening a prose lint to a new fence language is a lint-surface change — extend the checker in the same change as the first content it will read.** Text inside a fence language the checker cannot parse is unclassified, so a rule violation written in the new syntax passes silently and the guarantee the lint advertises is weaker than it reads. Add the language to the extractor and land fixtures for its shapes before, or together with, the first real block; the checker and the content are one change, not two.

## Reviews & Delegation

- **A "verbatim" criterion must name its sanctioned divergences, and drift-protection deferred to a note is unverified.** If a design says "copy X verbatim", enumerate at design time where the copy legitimately cannot be verbatim — banned terminology, or a context the source lacks (the inline path has no packet; the unlocked skill has no main agent to escalate to). Otherwise the criterion is unsatisfiable and a reviewer correctly records a gap the implementer already knew about was coming; one requirement was reported as a gap by two consecutive reviews on exactly this basis. The same applies to any "keep these in sync" instruction: a design line telling a future agent to mirror a change in a commit message protects nothing, and reads to a reviewer as an unverified criterion. Either pin it (an assertion over both sources) or state plainly that it is knowingly unverified.

- **State the diff base explicitly in any packet/review recipe; a committed range cannot show uncommitted work.** A `<merge-base>` placeholder leaves each run to guess (the wrong guess silently reviews the wrong span), and a per-requirement packet needs its base pinned to the previous requirement's commit — the progress file's commit column is the source. Because `git diff <base>...HEAD` reads committed refs only, assemble the packet *after* committing the slice under review; otherwise new or edited files are invisible to the reviewer while the report still reads as complete.
- **Post-packet review fixes: re-verify with gates + targeted assertions, not a re-review.** Delegated reviewers report against a packet snapshot; by the time findings land, HEAD has moved. Apply each finding as a fix commit, re-run the full gate suite (`npm run check`), and add a targeted assertion for the fixed surface. When a finding was already closed by a post-packet commit (a stale-packet finding), record the staleness explicitly in the coverage note rather than rebuilding the packet to chase recency.
- **Test-first pins-before-edits breaks packet Commit-column monotonicity.** A requirement whose red assertions commit before earlier requirements' implementation commits (the pins-before-edits order) fails the packet helper's cross-row ancestry check. Keep the requirement's terminal commit in the Commit cell and narrate the pre-implementation commit in its execution-summary row.
- **Findings about *other* topics, surfaced during a review, must be written to disk before finalizing.** A review of topic A legitimately turns up defects in topic B; conversational context does not survive `/new`, and the disposal globs for A will not preserve notes about B. Write them to a file that the disposal pattern cannot match (a differently-named doc under `docs/plans/`), and note the discovery globs only surface `*-design.md`/`overview.md`, so the next brainstorm must be pointed at it explicitly.

## Testing

- **Acceptance criteria for a text deliverable must demand cited supporting artifacts, not keyword presence.** "Then the conclusion appears — no conclusion silently stands without its supporting rows" is the shape that catches real defects; "Then the file contains the string X" is the shape that produces a green suite over a broken contract. When the deliverable is a document, spec, or config rather than code, the criteria still must name an observable supporting artifact (a table row, a count, a cited location) that a reviewer can check. The single most valuable criterion written for a doc-only feature was the one phrased that way; the rest described markers and were reported as gaps by the same reviewer.
- **Meaningful tests, mirrored across brainstorming, executing-tasks, and here.** (1) **Test observable behavior** — assert on what the feature produces or changes (a return value, persisted/updated data, an emitted event, an HTTP response) through its public interface; these assertions keep passing as the implementation changes. (2) **Write a per-slice test when the slice has its own observable behavior** — when a slice is pure config or a trivial extraction, the feature E2E covers it and a per-slice test is unnecessary.
- **Assertions for new behavior need a marker that distinguishes new from old.** A token present in both models gives a false green — e.g. `/umbrella/` matched the old `<umbrella>-overview.md` filename placeholder before the new behavior landed; switched to `/status-free/`, a property only the new model has.
- **A verbatim pin is a transcription, not a contract — pair it with an independent check.** A test that pins a skill's exact disposal-glob lines freezes whatever the skill says, defect included (observed: digest pins held the `-notes.md` omission green until a reviewer read the criterion). For generated text that must satisfy an external contract, assert the contract property separately (the glob is present; the span terminates; the count matches the tree) so the pin and the property cannot agree on a wrong answer.
- **Character-window-scoped pins duplicated across checkers are paired constants.** When a verbatim-pin span is re-implemented in two places (a skill-lint window and a vitest window over the same paragraph), growing the pinned content moves one window past the other's cutoff — widen both together (observed: 700 vs 900 after a fill-rule paragraph grew).
- **When tests pin prose verbatim and the tests are out of scope, treat the pinned substrings as immovable scaffolding.** Reword *around* them — keep the exact substring inside the new sentence — instead of rewriting the sentence and breaking the pin. Two suite failures in one feature came from dropping a pinned clause while improving its neighbors; restoring the clause inside the new wording satisfied both the criterion and the pin. The inverse also holds: when the design **mandates** a new shape (prose → table, header line → table cell), the pins are part of the change — find every assertion over the old shape and re-anchor it in the same commit, rather than treating the pins as an excuse to keep the old prose.
- **Git fixtures that resolve revisions need history depth, not just commits.** `git rev-parse <sha>^`, `HEAD~3`, and span assertions all fail in a fresh repo whose first recorded commit has no parent — symbolic SHAs compound it. Seed the fixture repo with an `--allow-empty` commit before the recorded range so every parent reference resolves.
- **A fixture that violates the subject's input contract fails looking like a product defect — repair the fixture until the target assertion is what is failing.** Naming and placement rules the subject enforces (a progress file must be `<leaf>-progress.md` beside its design; a recorded root commit has no parent for a `parent-of-first-recorded-commit` lookup) reject a well-meaning fixture with a generic `error:` that reads as the feature being broken. Classify fixture-contract failures by their message, fix the fixture, and re-run before drawing any conclusion about the implementation; only a failure at the target assertion is evidence about the product.
- **Reset module-level extension state per test.** Extensions keep `let` module state (e.g. the guard's `phase`); tests that drive phase transitions must fire `session_start` in `beforeEach` (or at test start), otherwise declaration order silently determines pass/fail — green until a reorder, `.only`, or `--sequence.shuffle` breaks it. Verify with a shuffled run before shipping.
- **Test-doc wording assertions should match behavior, not exact sentences.** Prefer regexes over `toContain("exact phrase")` when asserting documentation; minor rewording of a doc sentence should not break three suites. Keep one canonical marker per contract (or a shared assertions helper) instead of copy-pasting the same phrase into multiple test files.

- **Lint rules live in an importable pure module; the script only wires them.** A lint script written as top-level side effects ending in `process.exit` cannot be imported by the test runner — importing it would execute the whole lint and kill the worker. Put the rule (allowlists, classifiers, traversal) in a module both the script and the tests import; the script keeps only the wiring and the exit code.
- **A byte-identity assertion over one shared constant makes an N-site edit self-verifying.** When a clause, header, or template is pinned identical across N files, changing the source constant and re-syncing the sites needs no new per-site assertions — the existing identity check fails on any straggler the edit missed. Prefer one pinned constant consumed by N sites over N independent pins; the failure mode is a straggler the check names for you.
- **An illustrative artifact written in a design doc is a draft — execute it against the real tree before pinning it.** Example scripts composed at design time encode the design's assumptions about layout and paths, and those assumptions are exactly what the real tree contradicts. Run the example once, repair it, and pin the corrected bytes; a design draft promoted straight to a pinned constant ships its assumptions as policy.

## Shell & Subprocess Traps

- **Run verification gates as separate commands, not `&&`-chains.** A `grep` with zero matches exits 1 and aborts the whole compound command, so a green suite piped through a grep misreports as a failure mid-chain. One gate per invocation keeps the exit code honest.
- **sed range-extraction of a repeated section: strip the terminator per-range, never to-EOF.** `sed -n '/START/,/END/p' | sed '/END/,$d'` works only for a single occurrence — with repeated sections the delete-to-EOF kills every later group. Use `sed '/END/d'` (strip each terminator line) and prove it with a fixture containing two groups; single-group fixtures cannot catch it.
- **Run long-lived external processes in the foreground of a subagent, never detached.** Backgrounded processes (nohup &) get reaped between the parent's tool calls in this harness — the run dies mid-flight with no error surfaced. To execute a long command, delegate to a subagent whose bash call runs it in the foreground and blocks; orphaned grandchildren may survive and keep writing transcripts, so identify runs by session id and mtime, not by parent liveness.
- **Linted TypeScript: use optional chaining.** Biome enforces `useOptionalChain` — write `x?.method()`, not `x && x.method()` (the `fgMark` helper treats undefined content as a fail).
- **Shell-quote every path a demonstrated script derives at runtime.** A script embedded in agent-facing instructions is copied into working directories you do not control, so a path assembled by string concatenation (a variable interpolated into a directory-and-file path) breaks on any name containing a space or a shell metacharacter. Quote the derived path at the point of use, and include the quoting in the pinned bytes — the pin is what keeps the fix from being reverted by a later convenience edit.

## Context Economy

- **Name scratch artifacts so the disposal pattern matches them, or delete them explicitly.** Finalizing disposes the topic folder `docs/plans/<date>-<topic>/` wholesale — a scratch file parked at the `docs/plans/` top level, outside every folder, matches no disposal unit and survives finalizing as stray clutter. Keep scratch work **inside the topic folder** so it rides the disposal, or remove it by hand before disposing; verify with `ls` afterwards.

- **Gate and resume reads extract, never ingest.** A check that only needs a header line, a table, or a count must not read the file body — name the fields that can change the decision (header, table region, a count command) in the skill, so orientation costs scale with topic count instead of history size.

## Finalize & Disposal

- **Re-run the full suite after disposal, before merging.** Disposal changes the tree the green suite ran against: pre-finalize checks ran with the topic folder present, and an E2E pinned to a ship-time artifact inside it (the sample progress doc) went red on shipped `main` only after the folder was deleted. Any test asserting an artifact the design marks as ephemeral must also handle the disposed state (skip with the reason in the test name), and the finalize sequence's last gate belongs after the `rm -rf`, not before it.
